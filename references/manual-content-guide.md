# 手册内容编写指南（manual_spec.json）

手册正文由执行者（AI）阅读申请人提供的材料后撰写，写入一个 UTF-8 编码的 JSON 规格文件，
再由 `scripts/build_manual.py` 按固定版式渲染。**版式由脚本保证，内容由规格文件决定。**

## 1. 内容从哪里来

按优先级阅读申请人提供的全部材料（缺一不可，读不到先解决读取问题）：

1. 既有操作手册 / 说明书草稿（docx/md/txt）——最权威的章节与功能描述来源；
2. 需求方案、完整方案、立项/验收文档（md/docx/pdf）；
3. 代码仓库的 README、requirements.txt / pyproject.toml（核实技术栈与版本号）、
   入口脚本与主要包目录结构（核实功能模块划分）；
4. 必要时向申请人澄清，不允许凭印象编造功能、版本号、日期、单位名称。

内容红线：

- **忠实于材料**：功能、流程、状态名称、按钮文案、技术栈版本必须能在材料或源码中找到依据；
  材料没有的内容不写，宁可留占位也不虚构。
- 截图一律生成灰色占位框（`figure` 块），由申请人后期自行贴图；**禁止用 AI 生成界面截图冒充真实软件**。
- 涉密/内部真实数据（真实业务编号、人员姓名、业务台账、内部截图）不得写入手册；
  材料中若使用虚构演示数据，沿用并保持“演示/模拟”口径。
- 手册中不要出现 AI 生成痕迹、emoji、 Markdown 语法符号（`#`、`**`、反引号）。

## 2. 推荐章节结构（桌面业务软件通用，可按实际增删）

- 第一章 系统简介：背景 / 简介 / 目标用户 / 主要功能 / 优势与创新
- 第二章 系统运行环境：硬件环境 / 软件环境（操作系统、运行时与依赖版本、网络要求）
- 第三章 系统主要功能（操作人员）：按操作流程逐节描述，每节配操作步骤与界面截图
- 第四章 成果导出与资料维护：导出物与格式、备份恢复、版本更新、常见问题与术语说明

节编号与章标题严格对应（第一章用 1.1、1.2……；第三章用 3.1……）。
图编号全文连续（图1、图2……），表格不编号也可，保持全文一致。

## 3. JSON 结构

```json
{
  "meta": {
    "full_name": "某某管理系统",
    "version": "V1.0",
    "date_cn": "2026年10月8日",
    "manual_title": "操作手册"
  },
  "chapters": [
    {
      "title": "第一章  系统简介",
      "sections": [
        {
          "title": "1.1  背景",
          "blocks": [
            { "type": "para", "text": "正文段落，首行自动缩进2字符。" },
            { "type": "para", "text": "不缩进的段落（如环境清单）。", "indent": false },
            { "type": "bullets", "items": ["项目符号条目一", "条目二"] },
            { "type": "steps", "items": ["第一步内容，脚本自动加 1．", "第二步内容，自动加 2．"] },
            { "type": "table",
              "headers": ["列名1", "列名2"],
              "rows": [["值1", "值2"]],
              "widths": [3.2, 11.4] },
            { "type": "figure", "no": "图1", "title": "登录界面",
              "hint": "软件登录窗口，含账号密码输入框与登录按钮", "height_cm": 5.2 }
          ]
        }
      ]
    }
  ]
}
```

字段说明：

- `meta`：`full_name` 必须与将来申请表、页眉、code.docx 页眉**完全一致**；
  `version` 形如 `V1.0`；`date_cn` 用中文日期；`manual_title` 默认“操作手册”。
  可选 `header_text` 覆盖页眉文字（默认“全称 版本”）。
- 块类型：
  - `para`：普通段落；`indent:false` 用于清单式不缩进段落。
  - `bullets`：项目符号列表（脚本加“• ”悬挂缩进）。
  - `steps`：操作步骤，数组每项一步，脚本自动编号“1．2．3．”，**条目文本不要再手写编号**。
  - `table`：`headers` 行加粗居中；`widths` 为厘米数数组，合计约 14.6（版心宽）。
  - `figure`：截图占位框 + 居中图题；`no` 可省略（省略时按出现顺序自动编号）；
    `hint` 写清这张图应截什么界面，方便申请人对照贴图；`height_cm` 默认 5.2（5.0–5.6）。
- 目录由脚本根据 chapters/sections 自动生成，**不要在 JSON 里写目录**。

## 4. 写作风格

- 第三人称、说明书口吻：“点击……”“系统显示……”，不使用“你/我/大家”。
- 一节内先概述、再 `steps` 分步、最后注意事项；同一操作的按钮、状态名在全文保持同一写法。
- 状态、枚举值、固定列名等强结构信息优先用 `table` 表达。
- 每一节描述界面操作时，通常应配一个 `figure`；没有界面的纯说明节可不配图。
- 篇幅：正文一般 15–25 页；材料不足时如实写短，不灌水。

## 5. 生成与回填流程（脚本命令）

```powershell
# 1. 生成 docx（目录页码为占位 0）
python scripts/build_manual.py --spec manual_spec.json --out 软件全称.docx
# 2. WPS/Word 后台测量标题页码（不生成 PDF）
powershell -ExecutionPolicy Bypass -File scripts/get_heading_pages.ps1 -Path 软件全称.docx -Out heading_pages.json
# 3. 回填目录页码
python scripts/patch_toc.py --docx 软件全称.docx --headings heading_pages.json
# 4. 再次后台打开确认页数与目录（可选：get_heading_pages 再跑一次核对）
# 5. 人工审核通过后，经申请人明确同意才允许：
powershell -ExecutionPolicy Bypass -File scripts/export_pdf.ps1 -Path 软件全称.docx -Pdf 软件全称.pdf
```

注意：回填页码后**必须重新打开/重分页确认**；若正文改动导致页数变化，重做 2–3 步。
